# Question
Our order service retries a payment call when the provider times out. What could go wrong with that, and how would you make it safe?

# Answer
A timeout does not mean the payment failed, so a blind retry can charge the customer twice. The safe design sends an idempotency key with every attempt so the provider deduplicates, stores the key with the order before the first call, and uses bounded retries with exponential backoff and jitter. A strong answer also mentions reconciling unknown outcomes by querying the provider before retrying.

# Context
Sample fixture. Comes from `orders/payment_client.py`, where `charge()` is wrapped in a retry decorator with three attempts and the idempotency key is derived from the order id.

# Follow-up
## Question
Where would you store the idempotency key, and when would you write it?

## Answer
In the orders database, in the same transaction that moves the order to a pending-payment state, before the outbound call. Writing it afterwards or keeping it only in memory loses it on a crash, which brings the double charge back.

## Context
Sample fixture. `orders/models.py` has a `payment_attempt` table with a unique constraint on the key.
